# MVP 범위 정리

## 서비스 방향

이음(i-um)은 여행 전 예약 플랫폼이 아니라, 실제 여행 중에 사용자가 겪는
불편을 줄이는 여행 실행 도우미다.

트리플, 야놀자, 여기어때, 에어비앤비, 네이버 예약 등은 여행 전 탐색과
예약에 강점이 있다. 이음은 사용자가 이미 정한 여행 일정과 동행자 정보를
바탕으로, 여행 당일에 다음 행동과 지출 정산을 빠르게 처리하게 돕는다.

## MVP 한 줄 정의

여행 중 다음 일정과 지출을 한 흐름으로 이어주는 공동 여행 실행 앱.

## 핵심 가치

- 오늘 어디로 가야 하는지 바로 보여준다.
- 다음 장소까지의 이동 흐름을 끊기지 않게 연결한다.
- 정확한 길찾기는 Google Maps로 넘긴다.
- 여행 일정을 동행자와 함께 추가, 수정, 관리한다.
- 여행 중 결제한 금액을 빠르게 기록하고 공동 정산한다.
- 정산 결과는 여행에 초대된 모든 인원이 확인할 수 있다.
- 예약/숙소/액티비티 정보는 나중에 가져올 수 있도록 확장한다.

## 제품 포지션

### 하지 않는 것

- 자체 대중교통 내비게이션 엔진 구현
- Google Maps 수준의 실시간 길찾기 재구현
- 모든 예약 플랫폼과 초기부터 직접 API 연동
- 트리플처럼 여행 콘텐츠/예약/커머스를 전부 제공
- 복잡한 권한 체계와 기업용 협업 기능 제공

### 집중하는 것

- 여행 일정 실행 화면
- 동행자와 함께 수정하는 공동 일정
- 장소 간 이동 흐름
- Google Maps 길찾기 연결
- 여행 중 빠른 지출 기록
- 동행자 기준 공동 정산
- 일정, 장소, 지출, 정산을 한 여행 맥락에 묶기

## MVP 우선순위

| 순위 | 기능 | 우선순위 | MVP 포함 |
|------|------|----------|----------|
| 1 | 일정 등록 + 경로 보여주기 | 높음 | 포함 |
| 2 | Google Maps 연동 | 높음 | 포함 |
| 3 | 동행자 초대 + 공동 일정 관리 | 높음 | 포함 |
| 4 | 사용 금액 등록 + 공유 정산 | 높음 | 포함 |
| 5 | 외부 예약/서비스 연동 | 낮음 | 제외 |

## MVP 1. 일정 등록 + 경로 보여주기

### 목표

사용자가 여행 날짜별로 방문 장소를 등록하고, 오늘 일정에서 다음 장소와
전체 동선을 쉽게 파악할 수 있게 한다.

### 핵심 사용자 문제

여행 중에는 전체 계획표보다 "지금 다음에 어디로 가야 하는지"가 더 중요하다.
일정 앱처럼 모든 정보를 나열하면 현장에서 판단하기 어렵다.

### 주요 기능

- 여행 생성
  - 여행 이름
  - 시작일
  - 종료일
  - 기본 통화

- 일자별 일정 관리
  - Day 1, Day 2 등 날짜별 일정 구성
  - 각 Day 안에 장소를 순서대로 등록

- 장소 등록
  - 장소명
  - 주소
  - 좌표
  - 장소 타입
    - 관광지
    - 식당
    - 숙소
    - 카페
    - 쇼핑
    - 기타

- 일정 순서 변경
  - 같은 Day 안에서 장소 순서 변경
  - 순서 변경 시 동선 정보 재계산

- 오늘의 실행 화면
  - 현재 진행 중인 Day 표시
  - 다음 장소 카드 표시
  - 남은 장소 목록 표시
  - 도착 처리
  - 스킵 처리
  - 숙소로 이동 버튼

- 경로/동선 표시
  - 장소 간 직선 거리 또는 예상 거리 표시
  - 장소 간 예상 이동 시간 표시
  - 지도 위에 일정 순서 표시
  - 각 장소를 번호 핀으로 표시

### UX 방향

일정표 중심이 아니라 실행 화면 중심으로 설계한다.

예시:

```text
다음 장소
우메다 공중정원

도톤보리에서 약 28분
영업 종료까지 2시간 10분

[길찾기] [도착] [스킵] [숙소로]
```

### MVP에서 제외

- AI 일정 자동 생성
- 최적 동선 자동 추천
- 실시간 교통 상황 반영
- 앱 내부 턴바이턴 내비게이션
- 복잡한 지도 편집 기능

### 성공 기준

- 사용자가 여행 날짜별 장소를 등록할 수 있다.
- 오늘 일정에서 다음 장소를 바로 확인할 수 있다.
- 장소 순서에 따라 동선을 확인할 수 있다.
- 도착/스킵으로 다음 장소가 자연스럽게 넘어간다.

## MVP 2. Google Maps 연동

### 목표

정확한 길찾기와 실시간 대중교통 안내는 Google Maps로 넘기고, 이음은
여행 맥락에 맞는 길찾기 진입점을 제공한다.

### 핵심 사용자 문제

여행 중 매번 Google Maps에서 다음 목적지를 검색하는 것은 번거롭다. 특히
여러 장소를 순서대로 방문할 때마다 출발지와 도착지를 다시 입력해야 한다.

### 주요 기능

- 다음 장소 길찾기
  - 현재 위치에서 다음 장소까지 Google Maps 열기
  - 이전 장소에서 다음 장소까지 Google Maps 열기

- 이동 모드
  - 대중교통
  - 도보
  - 자동차

- 숙소 이동
  - 현재 위치에서 숙소까지 길찾기
  - 마지막 장소에서 숙소까지 길찾기

- 장소별 지도 링크
  - Google Maps 앱 또는 웹 열기
  - 장소 주소 복사
  - 장소명 원문 표시

### UX 방향

길찾기 버튼은 항상 현재 맥락을 알고 있어야 한다.

예시:

```text
[현재 위치에서 길찾기]
[도톤보리에서 길찾기]
[숙소로 돌아가기]
```

### 기술 방향

- Google Maps URL Scheme 또는 Universal Link 사용
- `origin`, `destination`, `travelmode=transit` 기반 길찾기 연결
- 앱 내부에서는 경로 요약과 실행 흐름만 관리

### MVP에서 제외

- 자체 대중교통 경로 계산
- Google Navigation SDK 기반 인앱 내비게이션
- 대중교통 실시간 위치 추적
- 환승 알림
- 하차 알림

### 성공 기준

- 사용자가 검색 없이 다음 목적지 길찾기를 열 수 있다.
- 현재 위치 기준 길찾기와 일정상 이전 장소 기준 길찾기를 구분할 수 있다.
- 숙소 복귀 길찾기를 빠르게 실행할 수 있다.

## MVP 3. 동행자 초대 + 공동 일정 관리

### 목표

여행에 타인을 초대하고, 초대된 인원이 같은 여행 일정을 함께 추가, 수정,
관리할 수 있게 한다.

### 핵심 사용자 문제

여행 일정은 보통 한 명이 혼자 만드는 것이 아니라 동행자와 계속 조율하면서
바뀐다. 메신저로 장소를 주고받고 한 명이 수동으로 반영하면 누락과 중복이
생기기 쉽다.

### 주요 기능

- 동행자 초대
  - 초대 링크 생성
  - 초대 링크 공유
  - 초대받은 사용자가 여행 참여

- 참여자 목록
  - 여행 참여자 확인
  - 참여자 이름 표시
  - 참여자별 역할 표시

- 공동 일정 편집
  - 참여자가 장소 추가
  - 참여자가 장소 수정
  - 참여자가 장소 삭제
  - 참여자가 장소 순서 변경
  - 참여자가 도착/스킵 상태 변경

- 변경자 표시
  - 장소를 누가 추가했는지 표시
  - 최근 수정자를 표시
  - MVP에서는 상세 변경 이력보다 최소한의 신뢰 정보만 제공

### 권한 모델

MVP에서는 단순한 권한만 제공한다.

```text
Owner
- 여행 삭제 가능
- 참여자 초대 가능
- 참여자 제거 가능
- 일정 수정 가능
- 지출 등록/수정 가능
- 정산 확인 가능

Member
- 일정 수정 가능
- 지출 등록/수정 가능
- 정산 확인 가능
```

### UX 방향

협업 기능은 업무 도구처럼 복잡하게 만들지 않는다. 사용자는 여행 화면 안에서
자연스럽게 "같이 보고 같이 고친다"는 느낌을 받아야 한다.

예시:

```text
오사카 3박 4일
민수, 지영, 현우와 함께 여행 중

Day 2
도톤보리
지영이 추가함

[장소 추가] [초대]
```

### MVP에서 제외

- 실시간 동시 편집 커서
- 상세 변경 이력 타임라인
- 댓글/투표 기반 일정 조율
- 역할 세분화
- 읽기 전용 참여자

### 성공 기준

- 사용자가 여행에 동행자를 초대할 수 있다.
- 초대된 사용자가 같은 여행 일정을 볼 수 있다.
- 초대된 사용자가 장소를 추가, 수정, 삭제할 수 있다.
- 일정 변경 내용이 다른 참여자에게 반영된다.

## MVP 4. 사용 금액 등록 + 공유 정산

### 목표

여행 중 지출을 5초 안에 기록하고, 여행에 초대된 모든 인원이 같은 정산
결과를 확인할 수 있게 한다.

### 핵심 사용자 문제

여행 중에는 누가 얼마를 냈는지 매번 자세히 입력하기 귀찮다. 하지만 나중에
정산하려고 하면 장소, 결제자, 금액, 분할 대상을 기억하기 어렵다.

또한 정산은 개인 기록이 아니라 동행자 전체가 납득해야 하는 공동 결과다.
따라서 지출 내역과 정산 결과를 여행 참여자들이 함께 볼 수 있어야 한다.

### 주요 원칙

- 여행 중에는 대충 기록하게 한다.
- 앱이 장소, 시간, 통화, 카테고리, 기본 분할을 자동으로 붙인다.
- 기본 분할 대상은 여행 참여자 전체다.
- 예외만 나중에 수정하게 한다.
- 정산 결과는 여행 참여자 모두에게 동일하게 보여준다.

### 주요 기능

- 빠른 지출 등록
  - 현재 장소 카드에서 `+ 지출`
  - 금액 입력
  - 결제자 선택
  - 저장

- 자동 정보 연결
  - 현재 일정 장소 자동 연결
  - 현재 시간 자동 기록
  - 여행 기본 통화 자동 선택
  - 장소 타입 기반 카테고리 자동 추정

- 결제자 선택
  - 여행 참여자 중 결제자 선택
  - 최근 결제자를 기본값으로 표시

- 기본 정산 규칙
  - 여행 참여자 전체 1/N
  - 일부 인원만 분할 가능
  - 나만 사용한 지출로 변경 가능
  - 직접 금액 입력 가능

- 공유 지출 내역
  - 여행 참여자 모두가 지출 내역 조회
  - 지출별 결제자 표시
  - 지출별 분할 대상 표시
  - 지출별 연결 장소 표시

- 오늘 지출 요약
  - 오늘 총 지출
  - 내가 낸 금액
  - 내가 더 낸 금액 또는 덜 낸 금액
  - 확인 필요한 지출 수

- 여행 정산 결과
  - 사람별 총 결제 금액
  - 사람별 부담 금액
  - 사람별 차액
  - 최종 송금 결과
  - 모든 참여자가 같은 결과 확인

### UX 방향

현장에서는 폼을 최소화한다.

예시:

```text
도톤보리 근처
JPY

[ 3,200 ]

결제자: 나
분할: 전체 1/N

[저장]
```

저장 후에는 다음처럼 보여준다.

```text
3,200엔 저장됨
도톤보리 · 식비 추정 · 전체 1/N
[수정]
```

정산 화면은 개별 내역보다 최종 행동을 먼저 보여준다.

```text
최종 정산

민수 -> 지영 18,500원
현우 -> 지영 7,200원

[상세 내역 보기]
```

### 정리 모드

여행 중에 완벽하게 입력하지 못한 지출은 나중에 정리한다.

예시:

```text
확인 필요한 지출 3건

3,200엔 · 식비 추정
[전체] [나만] [직접 선택]
```

### MVP에서 제외

- 영수증 OCR
- 카드 결제 문자 자동 파싱
- 은행/카드사 연동
- 환율 자동 고정/정산 고도화
- 복잡한 예산 분석
- 카카오페이/토스 송금 연동
- 정산 완료/입금 확인 플로우

### 성공 기준

- 사용자가 장소 이동 중에도 5초 안에 지출을 기록할 수 있다.
- 대부분의 지출은 금액만 입력해도 정산 초안이 만들어진다.
- 여행 참여자 모두가 지출 내역을 확인할 수 있다.
- 여행 참여자 모두가 같은 최종 정산 결과를 볼 수 있다.
- 여행 종료 후 누가 누구에게 얼마를 보내야 하는지 확인할 수 있다.

## MVP 제외. 외부 예약/서비스 연동

### 우선순위

낮음. 초기 MVP에는 포함하지 않는다.

### 방향성

외부 서비스와 직접 경쟁하지 않고, 사용자가 이미 예약한 내용을 여행 실행에
필요한 정보로 정리해주는 방향이 적합하다.

대상 서비스 예시:

- 트리플
- 여기어때
- 야놀자
- 에어비앤비
- 네이버 예약
- 항공사
- 호텔 예약 서비스
- 투어/액티비티 예약 서비스

### 직접 API 연동이 어려운 이유

- 서비스별 공개 API가 제한적이다.
- 사용자 예약 데이터를 외부 앱에 넘기는 OAuth 구조가 일반적이지 않다.
- 제휴가 필요한 경우가 많다.
- 서비스마다 예약 화면, 문자, 메일 포맷이 다르다.
- 개인정보와 예약번호 등 민감 정보 처리 부담이 크다.

### 향후 가능한 접근

#### 1. 직접 입력

사용자가 예약 정보를 직접 입력한다.

- 숙소명
- 주소
- 체크인/체크아웃
- 예약번호
- 금액
- 전화번호

#### 2. 복사 붙여넣기 파싱

예약 문자나 메일 내용을 붙여넣으면 자동으로 정보를 추출한다.

#### 3. 스크린샷 OCR

예약 화면 캡처를 업로드하면 숙소명, 날짜, 주소, 금액을 추출한다.

#### 4. 공유하기 확장

다른 앱에서 예약 정보를 이음으로 공유하면 예약 카드 초안을 만든다.

#### 5. 캘린더 연동

Google Calendar 또는 Apple Calendar에 등록된 항공, 숙소, 식당 예약 일정을
가져온다.

#### 6. 메일 연동

Gmail, 네이버 메일 등에서 예약 메일을 분석한다. 단, 권한 심사와 개인정보
처리 부담이 크므로 후순위로 둔다.

#### 7. 공식 API/제휴 연동

사용자 규모가 생긴 이후 특정 서비스와 제휴하거나 공식 API를 검토한다.

### 향후 연결 UX

예약 정보를 가져오면 다음처럼 여행 실행 흐름에 연결한다.

- 숙소를 `lodging` 장소로 자동 추가
- 체크인/체크아웃 시간 표시
- 숙소 주소로 Google Maps 길찾기
- 예약번호/전화번호 빠른 확인
- 숙박비를 지출/정산에 반영
- 체크아웃 날 숙소 이동 플로우 제공

## 장소 데이터 원칙

장소는 전역 마스터 데이터가 아니라 여행 일정 안의 장소 스냅샷으로 다룬다.

- 사용자가 장소를 선택하면 해당 여행의 `TripPlace`로 저장한다.
- `TripPlace`에는 선택 당시의 장소명, 주소, 좌표, 장소 타입, provider place id
  등 MVP 실행 화면에 필요한 최소 정보만 저장한다.
- Google Places 등 외부 API에서 받은 장소 정보를 서비스 전체에서 영구 재사용하는
  장소 DB로 만들지 않는다.
- 외부 API 응답은 비용 절감을 위한 TTL 캐시로만 다루고, provider 약관을 기준으로
  저장 필드와 보관 기간을 제한한다.
- 여행 상세, 오늘 실행 화면, 정산 화면 조회만으로 Places API를 호출하지 않는다.
- 장소 검색과 선택 시점에 외부 API 호출을 집중시킨다.
- 장소가 폐업, 이전, 이름 변경될 수 있으므로 기존 일정을 자동 덮어쓰기하지 않고
  변경 가능성을 표시한 뒤 사용자가 업데이트, 유지, 대체 장소 선택 중 고르게 한다.

## 기술 방향

- Repository: monorepo
- Mobile: React Native + Expo
- API: Go
- HTTP Router: chi
- API Contract: OpenAPI
- OpenAPI Tooling: oapi-codegen
- DB: PostgreSQL
- SQL: sqlc + pgx
- Migration: goose

## 개발 원칙

- OpenAPI 계약을 먼저 정의한다.
- OpenAPI에서 Go server interface를 생성한다.
- OpenAPI에서 모바일 TypeScript client를 생성한다.
- Go API 서버는 chi 기반으로 구현한다.
- 정확한 길찾기는 Google Maps로 연결한다.
- 장소 데이터는 `TripPlace` 스냅샷과 provider TTL 캐시로 분리한다.
- 지출 기록은 빠른 초안 생성을 우선한다.
- 정산 결과는 여행 참여자 모두가 같은 화면으로 확인한다.
